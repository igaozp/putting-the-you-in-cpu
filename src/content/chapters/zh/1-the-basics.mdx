写这篇文章时，一次又一次让我吃惊的是：计算机其实有多*简单*。我到现在还是很难完全摆脱那种心理预期——总觉得背后会有更多复杂性或抽象层！如果你只记住一件事再继续读，那就是：看起来简单的东西，往往真的就那么简单。这种简单既很美，有时也非常、非常让人崩溃。

让我们从计算机最核心的工作原理开始。

## 计算机如何构建

计算机的*中央处理器*（CPU）负责所有计算。它是老大。是总指挥。你一开机它就开始吭哧吭哧跑，一条指令接一条指令地执行。

第一款量产 CPU 是 [Intel 4004](http://www.intel4004.com/)，由意大利物理学家兼工程师 Federico Faggin 在 60 年代末设计。它是 4 位架构，而不是我们今天用的 [64 位](https://en.wikipedia.org/wiki/64-bit_computing)系统，也远比现代处理器简单——但其中不少「简单」的本质，至今仍然成立。

CPU 执行的「指令」不过是二进制数据：一两个字节表示执行哪条指令（操作码 opcode），后面跟着执行该指令所需的数据。我们所说的*机器码*，就是一连串这样的二进制指令。[汇编](https://en.wikipedia.org/wiki/Assembly_language)是一种便于阅读和编写机器码的语法，比原始比特好懂得多；它总会被编译成 CPU 真正能读懂的二进制。

<img src='/images/assembly-to-machine-code-translation.png' loading='eager' style='max-width: 400px;' alt='示意图：机器码与汇编如何互译。双向箭头连接三组例子：Machine Code (Binary) 后跟 3 字节二进制；Machine Code (Hex) 后跟对应十六进制（0x83, 0xC3, 0x0A）；Assembly 后跟 "add ebx, 10"。颜色标注表明每个字节对应汇编中的一个部分。' width='935' height='505' />

> 补充：指令并不总像上例那样与机器码 1:1 对应。例如 `add eax, 512` 会翻译成 `05 00 02 00 00`。
> 
> 第一个字节（`05`）是专门表示「把 EAX 寄存器与一个 32 位数相加」的操作码。后面几个字节是 512（`0x200`）的[小端](https://en.wikipedia.org/wiki/Endianness)字节序。
>
> Defuse Security 做了一个[很好用的工具](https://defuse.ca/online-x86-assembler.htm)，可以用来玩汇编和机器码之间的互译。

RAM 是计算机的主内存，一块多用途的大空间，存放所有正在运行程序用到的数据——包括程序代码本身，以及操作系统核心代码。CPU 总是直接从 RAM 读取机器码；代码不加载进 RAM 就无法运行。

CPU 里有一个*指令指针*（instruction pointer），指向 RAM 中下一条要取指令的位置。每执行完一条指令，CPU 移动指针，然后重复。这就是*取指-执行循环*（fetch-execute cycle）。

<img src='/images/fetch-execute-cycle.png' loading='lazy' style='max-width: 360px; margin: 0 auto;' alt='取指-执行循环示意图。两个文本气泡：第一个标 "Fetch"，文案为「从当前指令指针处读取内存中的指令」；第二个标 "Execute"，文案为「运行指令然后移动指令指针」。两者互相指向，表示循环过程。' width='848' height='458' />

执行完一条指令后，指针会前进到该指令在 RAM 中紧挨着的后面，从而指向下一条指令。这就是代码能「跑起来」的原因！指令指针一路往前冲，按机器码在内存中存放的顺序执行。有些指令可以让指令指针跳到别处，或根据条件跳到不同地方；可复用代码和条件逻辑因此成为可能。

这个指令指针存在一个[*寄存器*](https://en.wikipedia.org/wiki/Processor_register)里。寄存器是极小的存储单元，CPU 读写它们极快。每种 CPU 架构都有一套固定的寄存器，用途从计算过程中的临时值，到配置处理器本身，不一而足。

有些寄存器可直接从机器码访问，比如前面图里的 `ebx`。

另一些寄存器只由 CPU 内部使用，但往往也能通过专用指令更新或读取。指令指针就是一例：不能直接读，但可以用跳转指令等方式更新。

## 处理器很「天真」

回到最初的问题：当你在电脑上运行一个可执行程序时会发生什么？首先会有一堆魔法把准备工作做完——我们后面会细讲——但过程的终点是：某处文件里有了机器码。操作系统把它加载进 RAM，并让 CPU 把指令指针跳到 RAM 中的那个位置。CPU 照常跑取指-执行循环，于是程序开始执行！

（这对我来说又是一个「被自己吓一跳」的瞬间——说真的，你现在用来读这篇文章的程序，就是这样跑的！你的 CPU 正按顺序从 RAM 里取浏览器的指令并直接执行，它们正在渲染这篇文章。）

<img src='/images/instruction-pointer.png' loading='lazy' style='max-width: 400px;' alt='示意图：RAM 中一串机器码字节。高亮字节被标为「Instruction Pointer」的箭头指向，另有箭头表示指令指针在 RAM 中向前移动。' width='935' height='372' />

事实证明，CPU 的世界观超级朴素：它们只看得见当前指令指针和一点内部状态。进程完全是操作系统层的抽象，不是 CPU 原生理解或追踪的东西。

*\*挥挥手\* 进程是 ~~操作系统开发者~~ 大字节资本为了多卖电脑编出来的抽象*

对我来说，这引出的问题比回答的还多：

1. 如果 CPU 不懂多进程，只是顺序执行指令，它怎么不会卡死在正在运行的那个程序里？多个程序怎么同时跑？
2. 如果程序直接在 CPU 上跑，而 CPU 又能直接访问 RAM，为什么代码不能访问其他进程的内存，甚至——天哪——内核的内存？
3. 说到这个，是什么机制阻止每个进程执行任意指令、对你的电脑为所欲为？**系统调用到底是个什么鬼？**

关于内存的问题值得单独成章，见[第 5 章](/zh/the-translator-in-your-computer)——一句话概括：大多数内存访问其实会经过一层间接映射，整个地址空间都会被重映射。眼下我们先假装程序可以直接访问全部 RAM，而且电脑一次只能跑一个进程。这两个假设我们之后都会拆掉。

是时候跳进第一个兔子洞了——那里满是系统调用和安全环（security rings）。

> **补充：内核到底是啥？**
> 
> 你的电脑的操作系统，比如 macOS、Windows 或 Linux，是运行在电脑上、让各种基础功能可用的软件集合。「基础功能」本身就很宽泛，「操作系统」也一样——问不同的人，可能还包括默认附带的应用、字体和图标。
> 
> 而内核（kernel）是操作系统的核心。你开机时，指令指针从某个程序开始执行。那个程序就是内核。内核几乎可以完全访问电脑的内存、外设和其他资源，并负责运行安装在电脑上的软件（即用户态程序，userland programs）。内核为何有这些权限、用户态程序为何没有——我们会在全文中慢慢讲清楚。
>
> Linux 只是一个内核，还需要大量用户态软件（如 shell、显示服务器）才能真正好用。macOS 的内核叫 [XNU](https://en.wikipedia.org/wiki/XNU)，偏 Unix 风格；现代 Windows 内核叫 [NT Kernel](https://en.wikipedia.org/wiki/Architecture_of_Windows_NT)。

## 双环统治一切

处理器所处的*模式*（有时也称特权级或环，ring）决定了它能做什么。现代架构至少有两种：内核/监管模式（kernel/supervisor mode）和用户模式（user mode）。架构可能支持更多模式，但如今常用的主要就是内核模式和用户模式。

在内核模式下，几乎无所不能：CPU 可执行任何受支持的指令、访问任何内存。在用户模式下，只允许指令的一个子集，I/O 和内存访问受限，许多 CPU 设置也被锁住。一般而言，内核和驱动运行在内核模式，应用运行在用户模式。

处理器启动时处于内核模式。在执行程序之前，内核会发起切换到用户模式。

<img src='/images/kernel-mode-vs-user-mode.png' loading='lazy' style='max-width: 500px; margin: 0 auto;' alt='两张仿 iMessage 截图对比用户模式与内核模式保护。第一张标 Kernel Mode：右侧说「读这块受保护的内存！」，左侧回「好的亲 :)」。第二张标 User Mode：右侧同样请求，左侧回「不行！段错误！」' width='1072' height='433' />

真实架构中的例子：在 x86-64 上，当前特权级（CPL）可从名为 `cs`（代码段）的寄存器读取。具体来说，CPL 在 `cs` 寄存器的两个[最低有效位](https://en.wikipedia.org/wiki/Bit_numbering)里。这两位可表示 x86-64 的四个环：0 环是内核模式，3 环是用户模式。1、2 环设计给驱动用，但只有少数老旧小众操作系统会用。例如若 CPL 位是 `11`，CPU 就在 3 环：用户模式。
 
## 系统调用到底是什么？

程序跑在用户模式，因为不能把电脑的完全控制权交给它们。用户模式尽职尽责，挡住了对电脑大部分资源的访问——但程序*总得*能访问 I/O、分配内存、与操作系统交互！为此，用户态软件必须请求操作系统内核帮忙。操作系统再实现自己的安全保护，防止程序搞破坏。

如果你写过与 OS 交互的代码，大概认得出 `open`、`read`、`fork`、`exit` 这类函数。在几层抽象之下，它们都通过*系统调用*（system call）向 OS 求助。系统调用是一种特殊过程：让程序从用户空间转入内核空间，从程序代码跳进操作系统代码。

用户空间到内核空间的控制权转移，靠的是一种处理器特性，叫[*软件中断*](https://en.wikipedia.org/wiki/Interrupt#Software_interrupts)：

1. 启动过程中，操作系统会在 RAM 里放一张叫[*中断向量表*](https://en.wikipedia.org/wiki/Interrupt_vector_table)（IVT；x86-64 称之为[中断描述符表](https://en.wikipedia.org/wiki/Interrupt_descriptor_table)）的表，并注册给 CPU。IVT 把中断号映射到处理代码的指针。

  <img src='/images/interrupt-vector-table.png' loading='lazy' style='max-width: 300px; margin: 0 auto;' alt='标为「Interrupt Vector Table」的表格。第一列编号从 01 到 04，第二列「Handler Address」是随机的 8 字节十六进制数。表底写着「以此类推…」' width='555' height='463' />

2. 然后，用户态程序可用类似 [INT](https://www.felixcloutier.com/x86/intn:into:int3:int1) 的指令，让处理器在 IVT 中查找给定中断号，切换到内核模式，并把指令指针跳到 IVT 中存储的地址。

这段内核代码结束后，用类似 [IRET](https://www.felixcloutier.com/x86/iret:iretd:iretq) 的指令告诉 CPU 切回用户模式，并把指令指针回到触发中断时的位置。

（如果你好奇：Linux 上系统调用用的中断号是 `0x80`。可在 [Michael Kerrisk 的在线 man 页目录](https://man7.org/linux/man-pages/man2/syscalls.2.html)读到 Linux 系统调用列表。）

### 封装 API：把中断抽象掉

关于系统调用，目前我们知道的是：

- 用户模式程序不能直接访问 I/O 或内存。它们必须请 OS 帮忙与外界交互。
- 程序可用 INT、IRET 这类特殊机器码指令把控制权交给 OS。
- 程序不能直接切换特权级；软件中断之所以安全，是因为处理器*已由 OS 预先配置*好要跳到 OS 代码的哪里。中断向量表只能在内核模式配置。

触发系统调用时，程序还得把数据传给操作系统：OS 需要知道执行哪一个具体系统调用，以及该调用需要的数据（例如要打开哪个文件名）。传数据的机制因操作系统和架构而异，通常是在触发中断前把数据放进特定寄存器或栈上。

各设备上系统调用方式的差异，意味着程序员为每个程序亲自实现系统调用既不现实。这样也会让操作系统不敢改中断处理，怕弄坏所有按旧方式写的程序。再说，我们现在一般也不再用纯汇编写程序——不能指望程序员一想读文件或分配内存就掉到汇编里。

<img src='/images/syscall-architecture-differences.png' loading='lazy' style='max-width: 650px; margin: 0 auto;' alt='图注：「System calls are implemented differently across architectures.」左侧是笑脸 CPU 收到二进制后吐出文件名 file.txt；右侧另一颗 CPU 收到同样二进制却一脸困惑恶心。' width='1057' height='360' />

于是操作系统在这些中断之上提供抽象层。可复用的高层库函数封装了必要的汇编指令：类 Unix 系统上由 [libc](https://www.gnu.org/software/libc/) 提供，Windows 上是 [ntdll.dll](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/libraries-and-headers) 的一部分。调用这些库函数本身不会切到内核模式，它们只是普通函数调用。库内部的汇编代码才会真正把控制权交给内核，也比外层的库例程更依赖具体平台。

当你在类 Unix 系统上的 C 里调用 `exit(1)` 时，该函数内部会在把系统调用操作码和参数放进正确的寄存器/栈/等位置之后，运行机器码触发中断。计算机真酷！

## 速度至上 / 来点 CISC

许多 [CISC](https://en.wikipedia.org/wiki/Complex_instruction_set_computer) 架构（如 x86-64）包含专为系统调用设计的指令，正是因为系统调用范式太普遍了。

Intel 和 AMD 在 x86-64 上协调得不太好；实际上有*两套*优化过的系统调用指令。[SYSCALL](https://www.felixcloutier.com/x86/syscall.html) 和 [SYSENTER](https://www.felixcloutier.com/x86/sysenter) 是 `INT 0x80` 一类指令的优化替代。对应的返回指令 [SYSRET](https://www.felixcloutier.com/x86/sysret.html) 和 [SYSEXIT](https://www.felixcloutier.com/x86/sysexit) 则设计为快速回到用户空间并恢复程序代码。

（AMD 与 Intel 处理器对这些指令的兼容性略有不同。对 64 位程序一般首选 `SYSCALL`，而 `SYSENTER` 对 32 位程序支持更好。）

更具代表性的是，[RISC](https://en.wikipedia.org/wiki/Reduced_instruction_set_computer) 架构往往没有这类特殊指令。Apple Silicon 基于的 RISC 架构 AArch64，对系统调用和软件中断都只用[一条中断指令](https://developer.arm.com/documentation/ddi0596/2021-12/Base-Instructions/SVC--Supervisor-Call-)。我觉得 Mac 用户过得还行 :)

呼，信息量很大！简单回顾一下：

- 处理器在无限的取指-执行循环中执行指令，本身没有操作系统或「程序」的概念。处理器的模式（通常存在寄存器里）决定可执行哪些指令。操作系统代码在内核模式运行，再切到用户模式跑程序。
- 要运行二进制，操作系统切到用户模式，把处理器指向代码在 RAM 中的入口点。因为只有用户模式权限，想与外界交互的程序需要跳到 OS 代码求助。系统调用是程序从用户模式切到内核模式、进入 OS 代码的标准化方式。
- 程序通常通过调用共享库函数来使用这些系统调用。库函数封装了软件中断或架构专用系统调用指令的机器码，把控制权交给 OS 内核并切换特权环。内核办完事，再切回用户模式返回程序代码。
